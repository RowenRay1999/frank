## Context

Phase 3 完成后，Frank 拥有完整的单人对话能力。但家庭场景中常见多人同时在场——爸爸在问天气，孩子走过来也想问问题。当前系统只能服务一个人。Phase 4 解决三个问题：多人并行服务、耗时任务不阻塞对话、能力可扩展。

**关键依赖**：Phase 2 的身份融合引擎已支持同时跟踪多个 embedding。Phase 3 的 LLM/TTS 管道已支持流式输出。

## Goals / Non-Goals

**Goals:**
- 多人检测（≥2 人脸或 ≥2 声纹）→ 多人会谈模式切换（3 秒确认防误触发）
- 并行会话：主用户继续在主输出设备，副用户指令路由到副输出设备
- 后台任务：压缩/下载/生成等耗时操作托管执行，进度可查，异常明确告知
- 技能插件：标准接口（manifest + handler + prompt），子进程隔离，自动发现

**Non-Goals:**
- 3 人以上同时对话的复杂场景（Phase 4 仅支持双人并行）
- 任务依赖管理（DAG 编排）
- 插件市场/远程分发
- 智能家居实际集成

## Decisions

### D1: 多人检测基于人脸计数 + 3 秒防抖

**决策**：摄像头管线已支持多脸追踪。当连续 3 秒检测到 ≥2 张不同人脸（不同 embedding 聚类），触发多人模式。3 秒窗口过滤"路过"误触发。

### D2: 输出设备路由使用通道绑定模型

**决策**：每个活跃会话绑定一个输出通道（主显示器+主音频 或 副显示器+副音频）。Python 端通过 PyAudio 设备 ID 枚举音频输出，Electron 端通过 screen API 枚举显示器。通道分配优先级：用户预设 > 空闲设备 > 降级（文字通知+排队）。

### D3: 任务管理系统采用本地队列 + SQLite 持久化

**决策**：每个用户独立任务队列，状态持久化到 SQLite（`tasks` 表）。应用重启后自动恢复未完成任务。任务执行在独立子进程中运行，超时/异常触发三级处理：
- 🟡 可自动恢复：网络超时 → 3 次指数退避重试
- 🟠 需用户决策：磁盘满 → 暂停+通知+提供选项
- 🔴 不可恢复：任务本身有问题 → 通知原因+建议

### D4: 技能插件采用子进程隔离模式

**决策**：每个插件在独立 Python 子进程中运行，通过 stdin/stdout JSON 通信。超时和内存限制由父进程监控：
- 即时指令：10s 超时，256MB 内存
- 托管任务：30min 超时，1GB 内存
超时 → SIGKILL → 异常处理流程。

### D5: 插件发现基于文件系统扫描

**决策**：启动时扫描 `skills/` 目录，每个子目录包含 `manifest.json` 即视为一个插件。插件 `prompt.md` 文本注入 LLM 系统提示词的"可用能力"部分。热加载：文件变更检测 → 重新扫描 → 更新 LLM 上下文。

## Risks / Trade-offs

- **[R1] 多人模式资源开销** → 双人脸追踪 + 双 LLM 会话，内存增量 ~200MB。降级策略：检测到性能压力时副用户仅文字响应（不启用 TTS）
- **[R2] 副输出设备不可用** → 副用户降级为文字通知+排队："B 也在等待回复"，排队超时后提示
- **[R3] 长时间运行任务占用资源** → 任务优先级调度：对话响应优先于后台任务，CPU/内存紧张时暂停低优先级任务
- **[R4] 插件代码安全性** → 子进程隔离 + 权限声明（manifest.permissions）+ 文件访问白名单
