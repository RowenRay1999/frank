## ADDED Requirements

### Requirement: 主人引导注册流程

Owner 通过成员管理面板发起手动注册，系统分四步引导完成人脸和声纹采集，并在最后一步验证融合识别效果。

#### Scenario: 正常注册流程完成

1. 前置条件：Owner 已登录，成员管理面板已打开，数据库中没有与该人脸/声纹匹配的记录。
2. Owner 点击"添加成员"按钮，进入注册步骤 1。
3. 步骤 1 界面弹出表单，要求输入显示名称（2-20 个字符，不允许与已有显示名称重复）和选择角色（Adult / Child / Guest，Owner 角色只能通过设备初始化设置）。
4. Owner 输入名称"王小明"并选择 Adult 角色，点击"下一步"。
5. 步骤 2 人脸注册开始：摄像头实时画面显示，系统在画面上覆盖人脸检测框和角度指示器（偏航角、俯仰角、翻滚角）。引导文案提示"请正对摄像头"。
6. 系统依次要求采集 5 个角度：正面、微向左转、微向右转、微抬头、微低头。当前进度以 3/5 形式显示。每个角度采集到合格帧（正面角度偏差 < 30 度，人脸区域 >= 80x80px，清晰度达标）后框变为绿色，自动进入下一个角度。
7. 第 5 个角度采集完成后，系统提取每帧的 512-dim 人脸 embedding 并计算均值，记录典型人脸距离。显示"人脸注册完成"，自动跳转至步骤 3。
8. 步骤 3 声纹注册开始：屏幕显示 3 句随机句子（从 50 句覆盖普通话声韵母的句子池中抽取，每句 10-15 字）。系统提示"请依次朗读以下句子"。
9. 用户朗读第 1 句，VAD 检测到有效语音段（时长 >= 1.5s，SNR > 15dB），系统自动切到第 2 句。若语音质量不达标，提示"声音太轻或有噪音，请重读一遍"。
10. 3 句全部通过后，系统提取每句的 192-dim 声纹 embedding 并计算均值。显示"声纹注册完成"，自动跳转至步骤 4。
11. 步骤 4 融合验证开始：系统实时采集当前画面的人脸和声音，运行融合识别引擎，计算与刚注册的 embedding 的匹配分数。
12. 匹配分数达到 0.75 以上，显示"验证通过！注册完成"。系统将新成员记录写入数据库，成员面板刷新显示新成员。
13. 后置条件：members 表中新增一条记录，display_name 为"王小明"，role 为 adult，face_embedding 和 voice_embedding 字段填入注册得到的平均嵌入向量。

#### Scenario: 注册过程中人脸/声纹质量不合格

1. 前置条件：Owner 进入注册步骤 2（人脸采集）第 3 个角度（微向右转）。
2. Owner 转动幅度过大，偏航角超过 30 度，人脸检测框变为红色，系统显示"角度过大，请微微向右转"。
3. Owner 连续 10 秒未调整到位，系统追加提示"可以看到你的左耳吗？保持只看到左耳的一半程度即可"。
4. Owner 调整到位后，检测框变绿，自动进入下一个角度。
5. 类似的，步骤 3 声纹注册中，若环境噪音过大导致 SNR 不达标连续 3 次，系统提示"环境噪音较大，建议到安静的地方继续注册"，并提供"稍后继续"选项保存当前进度。
6. 后置条件：若选择"稍后继续"，当前已采集的数据暂存到 session，下次进入注册流程时从中断处继续。

#### Scenario: 注册验证失败

1. 前置条件：步骤 4 融合验证开始。
2. 系统采集当前人脸和声音，融合识别分数为 0.55（低于 0.75 阈值）。
3. 系统显示"验证分数偏低，建议重新注册"。显示各模态单独分数：人脸分数 0.80、声纹分数 0.35。
4. 提示"声纹匹配分数较低，建议重做声纹注册"，并提供"重做声纹"按钮。
5. Owner 点击"重做声纹"，流程回到步骤 3 声纹注册。
6. 若再次验证仍然失败，提供"跳过验证"选项（允许在低置信度下完成注册，后续通过自适应更新逐步改善）。

### Requirement: 未识别人员自动发现

系统持续检测摄像头和麦克风输入，当发现未知人脸或声音特征（与所有已知成员的最大余弦相似度 < 0.5）时，在满足多重重叠条件后自动创建访客记录。

#### Scenario: 新访客自动发现并创建记录

1. 前置条件：数据库中有 5 个已注册成员（平均 face_embedding 各不同），无未识别访客记录。摄像头实时画面中出现一张新面孔。
2. 摄像头管线（InsightFace buffalo_l）检测到人脸，提取 512-dim face_embedding。
3. 识别引擎将新 embedding 与所有已知成员的 embedding 计算余弦相似度，最大值为 0.32（低于 0.5 阈值），判定为未知。
4. 同时音频管线未检测到该人说话，仅人脸模态可用。
5. 系统记录本次检测事件：unknown_face_embedding、timestamp、face_quality 分数。由于只有 1 次检测，暂不创建记录。
6. 第 2 次检测：50 秒后（间隔 >= 30s），同一张人脸再次出现。系统检测到该 face_embedding 与第 1 次的聚类距离 < 0.1，判定为同一人。当前累积检测计数 = 2。
7. 第 3 次检测：35 秒后，同一人脸再次出现。累积检测计数 = 3，达到触发条件。
8. 自动发现模块对 3 次检测的人脸 embedding 做逐元素平均，得到 avg_embedding。
9. 从 members 表查询当前最大序列号（假设已有访客-002），自增生成"访客-003"。
10. 系统在 members 表中插入新记录：serial_name = "visitor-003"，display_name = NULL，role = "guest"，face_embedding = avg_embedding，appearance_count = 3，created_at = now，last_active_at = now。
11. 后置条件：members 表新增一条未命名访客记录。自动发现模块将本次事件通知到 UI，待识别访客区新增条目"访客-003（出现 3 次）"。

#### Scenario: 单次误检测不触发自动创建

1. 前置条件：无。
2. 摄像头因光线变化或画面抖动误检测到一张"人脸"，提取 embedding。识别引擎匹配所有已知成员均 < 0.5。
3. 但该画面仅出现一次，后续 10 分钟内不再出现（不满足 >= 3 次且间隔 >= 30s 的条件）。
4. 系统不创建任何记录。该误检测数据在内存中被丢弃。
5. 后置条件：members 表无变化。

#### Scenario: 人脸质量不合格不触发自动创建

1. 前置条件：无。
2. 摄像头检测到一张人脸，但偏航角 45 度（超过 30 度限制），或人脸区域 60x60px（低于 80x80px 要求）。
3. 即使该人脸出现多次且间隔符合要求，每次检测时的质量门控均未通过，系统仍不创建访客记录。
4. 后置条件：members 表无变化。

### Requirement: 首次交互自动标注

未识别访客（已自动创建记录但尚未命名）首次与 Frank 对话时，系统主动询问称呼，并根据用户回复更新记录名称，角色保持 Guest。

#### Scenario: 访客首次说话，自动询问称呼并更新

1. 前置条件：访客-003 已自动创建（display_name = NULL，role = guest，appearance_count = 3）。该访客此前从未与系统进行语音交互。
2. 访客-003 出现在摄像头前，系统识别为访客-003。访客说"今天天气怎么样"。
3. 身份融合引擎输出身份为访客-003（guest 角色）。状态机进入 Auth 状态，携带角色上下文。
4. 系统判断"访客-003 首次语音交互"，触发自动标注流程。
5. Frank 语音回应："你好，我是第一次听到你的声音。请问怎么称呼你？"
6. 用户回答："叫我李叔叔吧"。
7. 系统解析用户回答，进行简单清洗（去首尾空格），长度为 5 个字符，未超过 20 字符限制。检查 display_name 是否重复（"李叔叔"不在已有名称中）。
8. 系统将 members 表中访客-003 的 display_name 更新为"李叔叔"。保留原有的 face_embedding 数据。首次交互标记 first_interaction_declined = 0。
9. Frank 语音回应："好的李叔叔！以后我就这么称呼你。"
10. 后置条件：访客-003 的 display_name 变为"李叔叔"，role 仍为 guest。成员管理面板待识别区中显示"李叔叔（待主人升级）"。

#### Scenario: 访客拒绝命名

1. 前置条件：访客-005（display_name = NULL）首次说话。
2. Frank 询问"请问怎么称呼你？"。
3. 用户回答："不用了"或"不用"。
4. 系统识别为拒绝意图。设置 first_interaction_declined = 1。
5. Frank 回应："好的，那我先保留默认称呼。下次想改名随时告诉我就好。"
6. 后置条件：访客-005 保持 display_name = NULL，first_interaction_declined = 1。同一访客后续不再触发命名询问（除非主人手动重置）。

#### Scenario: 名称重复冲突

1. 前置条件：已有已识别成员"李叔叔"，访客-003（display_name = NULL）首次说话。
2. Frank 询问称呼，用户回答："李叔叔"。
3. 系统检测到"李叔叔"在已识别成员中已存在。提示："这个名字已经被使用了，可以换一个称呼吗？比如王叔叔、张叔叔？"
4. 用户回答："那叫我李伯伯吧"。
5. 系统检查"李伯伯"不存在，更新 display_name = "李伯伯"。
6. Frank 回应："好的李伯伯！以后我就这么称呼你。"

### Requirement: 主人标识面板 UI

成员管理面板包含已识别成员区和待识别访客区，Owner 可在面板上完成查看、编辑、删除、识别等操作。

#### Scenario: 面板加载显示正确的成员和访客信息

1. 前置条件：Owner 已登录，数据库中已识别成员 3 人（王小明-owner、张丽-adult、小波-child），待识别访客 2 人（访客-003、访客-007）。
2. Owner 点击主界面的"成员管理"入口。
3. 面板加载并呈现两栏布局：
   - 左栏/上栏"已识别成员"列表，按最近活跃时间倒序排列：王小明（Owner 标签，头像，今日活跃）、张丽（Adult 标签，头像，昨天活跃）、小波（Child 标签，头像，3 天前活跃）。每行右侧有 [编辑] 和 [删除] 按钮。
   - 右栏/下栏"待识别访客"列表，按最近出现时间倒序排列：访客-007（出现 8 次，最后出现 2 小时前）、访客-003（出现 12 次，最后出现昨天）。每行右侧有 [识别] 按钮。
4. 后置条件：面板正确渲染所有成员信息。

#### Scenario: 编辑已识别成员信息

1. 前置条件：面板已打开，王小明（owner）成员行可见。
2. Owner 点击王小明行的 [编辑] 按钮。
3. 弹窗显示编辑表单：名称（王小明）、角色（owner 灰化不可修改，系统限制仅 1 个 owner）。可选操作："重新采集人脸"、"重新采集声纹"。
4. Owner 将名称改为"王大明"，点击保存。
5. 系统更新 members 表 display_name 为"王大明"。面板刷新显示新的名称。
6. 后置条件：members 表对应记录的 display_name 已更新。

#### Scenario: 待识别访客区显示正确计数和时间

1. 前置条件：访客-003 出现 12 次，最后出现昨天。访客-007 出现 8 次，最后出现 2 小时前。
2. 面板中待识别区显示：
   - 访客-007：出现 8 次，最后 2 小时前
   - 访客-003：出现 12 次，最后 1 天前
3. 时间显示格式：1 小时内显示"X 分钟前"，1-24 小时显示"X 小时前"，1-7 天显示"X 天前"，7 天以上显示日期。

### Requirement: 主人标识访客流程

Owner 在标识面板点击待识别访客的 [识别] 按钮，完成命名、角色选择和可选合并操作。

#### Scenario: 将访客识别为新成员

1. 前置条件：面板已打开，访客-003 显示在待识别区（appearance_count = 12，last_seen = 昨天）。
2. Owner 点击访客-003 行的 [识别] 按钮。
3. 弹窗显示：序列名"访客-003"、出现次数 12、最近活跃"昨天"、已有生物特征数据情况（人脸已注册、声纹未注册）。
4. 表单输入：显示名称（预填充空，可输入 2-20 字符）、角色选择下拉（Adult / Child / Guest，Owner 不在此选择）。可选复选框"合并到已有成员"。
5. Owner 输入"王叔叔"，选择 Adult 角色，不勾选合并，点击确认。
6. 系统执行：更新 members 表对应记录：display_name = "王叔叔"，role = "adult"，labeled = true（从未命名访客转为已识别成员）。保留原有的 face_embedding。初始化声纹 embedding 为空（后续可补充）。
7. 弹窗关闭，面板刷新。待识别区移除访客-003。已识别成员区新增"王叔叔（Adult）"。
8. 后置条件：members 表中访客-003 的记录从访客转为已识别成员。

#### Scenario: 将访客合并到已有成员

1. 前置条件：面板已打开，访客-007 在待识别区。已有成员"小明"（child）。Owner 确认访客-007 就是小明（可能因为小明换了发型导致识别失败）。
2. Owner 点击访客-007 的 [识别]，勾选"合并到已有成员"。
3. 合并目标选择下拉框显示所有已识别成员列表（按名称排序）：小波、小明、张丽、王大明。
4. Owner 选择"小明"。
5. 系统检查合并合理性：若访客-007 的 face_embedding 与"小明"的 face_embedding 余弦相似度 < 0.3，提示"人脸特征差异较大，确认合并？"Owner 确认。
6. Owner 点击确认合并。
7. 系统执行：
   - 读取访客-007 的 face_embedding，追加到"小明"的 embedding 候选池（增加多样性）。
   - 若"小明"已有声纹 embedding，访客-007 的声纹数据也同理追加。
   - embedding 池扩充后重新计算加权平均作为新的基线 embedding。
   - 删除访客-007 的记录。
   - 更新"小明"的 appearance_count += 访客-007 的 8 次。
8. 后置条件：members 表中减少一条访客记录。"小明"的 face_embedding 更新为融合后的新向量，appearance_count 增加。

#### Scenario: 识别时声纹补充注册

1. 前置条件：访客-003 已有 face_embedding 但无 voice_embedding。Owner 点击识别，输入名称，选择角色。
2. 系统检测到该访客缺少声纹数据，弹窗提示"该访客还没有声纹记录，是否现在补充采集？【跳过】/【立即采集】"。
3. Owner 选择"立即采集"。
4. 系统进入快速声纹注册模式：只需朗读 1 句句子（约 15 秒），提取 192-dim voice_embedding。
5. 采集完成后，回到识别确认弹窗。Owner 点击确认完成识别。
6. 后置条件：该成员同时拥有 face_embedding 和 voice_embedding，双模态识别可用。

### Requirement: 成员删除

Owner 可删除已识别成员，删除时 embedding 物理擦除，聊天记录可选项处理。

#### Scenario: Owner 删除普通成员

1. 前置条件：已识别成员列表中有"王叔叔"（adult）和"小波"（child）。Owner 王大明在面板上。
2. Owner 点击"王叔叔"行的 [删除] 按钮。
3. 系统弹出删除确认弹窗，显示成员信息："王叔叔（Adult）"，警告"删除后该成员的所有生物特征数据将永久清除"。
4. 弹窗显示聊天记录处理方式单选：○ 匿名化保留（默认选中）/ ○ 一并删除。
5. Owner 选择"匿名化保留"，点击确认删除。
6. 系统执行：
   - 将 members 表中"王叔叔"记录的 face_embedding 和 voice_embedding 字段置为 NULL。
   - 执行 DELETE 删除成员记录。
   - 执行 VACUUM 回收 SQLite 页面空间（物理擦除 embedding 数据）。
   - chat_history 表中属于"王叔叔"的记录的 display_name 替换为"已删除用户"，member_id 置为 NULL。
   - skill_preferences 表通过外键 ON DELETE CASCADE 自动清理。
7. 删除完成后显示提示"成员'王叔叔'已删除"。
8. 后置条件：members 表中"王叔叔"记录已物理删除。聊天记录中的名称被匿名化。

#### Scenario: 聊天记录一并删除

1. 前置条件：同上，Owner 选择"一并删除"。
2. 系统执行 DELETE 级联删除该成员的所有聊天记录、技能偏好配置。
3. 后置条件：该成员的所有数据物理删除。

#### Scenario: 不允许删除唯一 Owner

1. 前置条件：系统中只有王大明一个 Owner 成员。
2. Owner 尝试删除自己或另一个 Owner（不存在）。
3. 若 Owner 点击自己的删除按钮，按钮灰化不可点击，悬停提示"不能删除唯一的设备主人"。
4. 后置条件：Owner 记录不被删除。

### Requirement: 自适应嵌入更新

每次成功识别时系统采集新 embedding 样本，每周执行加权平均更新基线 embedding。连续低置信度触发重新注册提示。

#### Scenario: 每周加权平均更新

1. 前置条件：王小明（adult）已注册超过 7 天，face_embedding 基线为 baseline_v1（512-dim 向量）。本周共成功识别王小明 20 次，每次识别均采集新的 face_embedding 并暂存到临时样本池。
2. 周调度器触发。读取王小明本周的 20 个 face_embedding 样本，计算逐元素平均值得到 week_avg。
3. 计算 new_baseline = 0.7 * baseline_v1 + 0.3 * week_avg。
4. 系统将成员表中王小明 face_embedding 字段更新为 new_baseline。
5. 清理本周临时样本数据（保留最近 90 天样本供回滚分析）。
6. 后置条件：王小明 face_embedding 更新为新基线。下次识别将使用新 embedding 匹配。

#### Scenario: 当周无成功识别时基线保持不变

1. 前置条件：小波（child）本周外出旅游，系统 7 天内未检测到小波的面孔或声音，样本池为空。
2. 周调度器触发，检测到本周样本数为 0。
3. new_baseline = old_baseline（保持不变，衰减系数不计）。
4. 后置条件：小波的 embedding 基线未更新。

#### Scenario: 连续低置信度触发重新注册提示

1. 前置条件：王小明最近换了发型，识别系统对其每日平均融合分数在 0.58-0.65 之间（持续低置信度区间 0.55-0.70）。
2. 低置信度监控模块检测到王小明连续 3 个自然日处于此区间。
3. 系统检查 14 天冷却期：王小明上次被提示重新注册是 20 天前（已超过 14 天冷却期），允许触发提示。
4. Frank 主动提示："最近识别你不太确定，鉴于我已经记录了一些新的样本，要更新你的面部和声音记录吗？只需 30 秒。"
5. 王小明回答"好的"。
6. 系统启动快速更新流程：仅需正面人脸（1 帧）+ 1 句语音（>=1.5s），提取新 embedding 直接替换基线 embedding。
7. 更新完成后 Frank 回应："已更新完成，现在识别会更准确。"
8. 后置条件：王小明 face_embedding 和 voice_embedding 更新为新提取的向量。冷却期重新开始计算。

#### Scenario: 冷却期内不重复提示

1. 前置条件：王小明 10 天前已触发过低置信度提示并被拒绝（"不用了"）。现在又连续 3 天低置信度。
2. 系统检查冷却期：距离上次提示仅 10 天 < 14 天冷却期。
3. 系统不触发提示。低置信度事件仅记录日志。
4. 后置条件：无用户交互。系统继续正常采集样本等待下次周更新。

### Requirement: 未识别访客自动清理

长期未出现的未识别访客自动清理生物特征数据，频繁访客豁免，Owner 可配置清理策略。

#### Scenario: 自动清理过期访客

1. 前置条件：members 表中有 3 个未识别访客：访客-003（appearance_count=2，last_active_at=40 天前）、访客-005（appearance_count=4，last_active_at=35 天前）、访客-007（appearance_count=6，last_active_at=50 天前）。
2. 系统每日检查清理条件。当前日期 - last_active_at >= 30 天。
3. 检查结果：
   - 访客-003：30 天门槛满足，appearance_count=2 < 5 → 标记待清理。
   - 访客-005：30 天门槛满足，appearance_count=4 < 5 → 标记待清理。
   - 访客-007：30 天门槛满足，但 appearance_count=6 >= 5 → 豁免，保留。
4. 系统向 Owner 推送预清理通知（见下个 Scenario）。
5. 3 天后，Owner 未干预，系统执行自动清理：
   - 访客-003 和访客-005 的记录从 members 表 DELETE。
   - 由于这两个访客从未与系统进行过交互（首次交互 declined），无聊天记录需要处理。
   - VACUUM 回收空间。
6. 后置条件：访客-003 和访客-005 从数据库物理删除。访客-007 保留（豁免）。

#### Scenario: 预清理通知

1. 前置条件：系统已标记访客-003 和访客-005 为待清理（距离清理执行还有 3 天）。
2. 系统向 Owner 推送通知（桌面通知 + 成员面板通知角标）：
   ```
   ┌─────────────────────────────────────┐
   │  访客清理提醒                       │
   │  以下访客已超过 30 天未出现，       │
   │  将于 3 天后自动清理生物特征数据：  │
   │                                     │
   │  · 访客-003（上次出现：40 天前）    │
   │  · 访客-005（上次出现：35 天前）    │
   │                                     │
   │  [查看详情]  [稍后处理]             │
   └─────────────────────────────────────┘
   ```
3. Owner 点击"查看详情"，打开成员面板待识别区，待清理访客以橙色标记显示。
4. Owner 可在清理前对访客执行识别（转为正式成员）操作以阻止清理。
5. 后置条件：通知已送达。若 Owner 在 3 天内将访客-003 识别为正式成员，则清理跳过该记录。

#### Scenario: Owner 禁用自动清理

1. 前置条件：所有未识别访客的自动清理规则默认开启。
2. Owner 打开设置 → 隐私与数据 → 自动清理。
3. 设置页面显示：
   - [开关] 自动清理未识别访客（默认开启）
   - 清理周期：30 天（可拖动 15-90 天）
   - 清理前通知：3 天（可拖动 0-7 天）
   - [开关] 保留频繁访客（出现 >= 5 次）（默认开启）
4. Owner 关闭"自动清理未识别访客"开关。
5. 系统将该设置写入配置（SQLite 配置表或本地 JSON 配置文件），清理调度器停止执行。
6. 但如果系统检测到时数据库中有超过 100 个未识别访客记录，且清理已关闭超过 30 天，发出通知"访客记录已超过 100 条，建议开启自动清理以节省存储空间"。
7. 后置条件：自动清理暂停。所有访客记录无论是否过期均保留。

#### Scenario: 已识别成员不参与自动清理

1. 前置条件：已识别成员"王叔叔"（adult）已 60 天未出现（去外地出差）。
2. 系统清理检查：王叔叔的 role 为 adult（非 guest），labeled = true，属于已识别成员。
3. 系统跳过该记录，不参与自动清理逻辑。
4. 后置条件：王叔叔的记录完整保留。
